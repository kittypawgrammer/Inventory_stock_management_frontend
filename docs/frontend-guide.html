1Overview

What the app is, in one look.

StockFlow is a Single Page Application for a small company. It manages stock (products, categories, suppliers), sales (customers, orders, order status), and people (users, roles and delegated tasks). It also asks a machine-learning model on the backend to predict how many days an order will take.

The frontend talks to a FastAPI backend over REST at http://localhost:8000/api/v1/.

📦 Inventory

Products, categories and suppliers. Full CRUD, plus a stock IN/OUT modal with a reason.

🧾 Sales

Customers and multi-line orders. Orders move through an 11-status state machine.

🤖 AI predictions

Predicts delivery days for an order, or for a manual "what-if" scenario.

✅ Tasks

Managers assign tasks to staff. A task gives staff edit rights on that one record.

👥 Users

The Super Admin changes user roles. A role change forces a fresh login.

📊 Dashboard

Stock value, low/out-of-stock alerts, recent orders and my tasks. It is role-aware.

UrlTree in simple words: the guard does not navigate by itself. It hands the router a "go here instead" address, such as /login?returnUrl=/products. The router cancels the current navigation and goes there in one clean step.
// auth.guard.ts
export const authGuard: CanActivateFn = (route, state) => {
  const router = inject(Router);
  if (getAccessToken()) { return true; }
  return router.createUrlTree(['/login'], { queryParams: { returnUrl: state.url } });
};

// role.guard.ts
export const roleGuard: CanActivateFn = (route) => {
  const userRole = currentRole();
  const allowed = (route.data['roles'] || []).map(parseRole).filter(r => r !== null);
  if (userRole !== null && allowed.includes(userRole)) { return true; }
  return inject(Router).createUrlTree(['/login']);
};

6Login, tokens & refresh

The most important technical part to explain.

Where the tokens live

TokenStored inWhy
Access token (JWT, short-lived)localStorage['stockflow_user_data'] and the session signalNeeded in the Authorization header, so JavaScript must be able to read it.
Refresh token (long-lived)An httpOnly cookie set by the backendJavaScript can't read it, so an XSS bug cannot steal it. It's sent automatically with withCredentials.

Login: function call chain

LoginComponent.onSubmit() └─ AuthService.login({email, password}) └─ POST auth/login (withCredentials → the backend also sets the refresh cookie) └─ startSession(access_token, role, username, user_id) auth-state.ts ├─ rejects the token if it is missing or expired ├─ roleFromToken(token) decodes the JWT; the JWT role wins over the response role ├─ localStorage.setItem('stockflow_user_data', …) └─ session.set(user) → the signal updates → the sidebar, buttons and guards react └─ SessionService effect() sees the new token → armFor(token) → timer = expiry − 60 s └─ router.navigate(['/dashboard'])

The session signal (auth-state.ts)

Write: private

Only startSession, restoreSession and clearSession call session.set.

Read: public

currentUser() is read-only. All the role helpers read it.

Why a signal?

Simple reads with no subscriptions to clean up, and an effect() can re-arm the refresh timer automatically.

Two ways the token gets refreshed

⏰ Proactive (normal case)

An effect() in SessionService watches the token. armFor() sets setTimeout for 60 s before expiry, then calls refresh(). Users almost never see a 401.

🛟 Reactive (backup)

If any API still returns 401, the interceptor calls session.refresh() and replays the original request with the new token.

The interceptor flow (auth.interceptor.ts)

Every requestAn auth URL (login, register, refresh, logout) gets only withCredentials. Every other URL gets withBearer(req, token), which adds the Authorization: Bearer … header and withCredentials.
↓
Response is a 401 on a non-auth URL?If it's any other error, or a 401 from an auth URL, it is rethrown. No loop.
↓ yes
session.refresh()A single shared call to POST auth/refresh (sends the cookie).
↓
Success → switchMapReplays the original request once with the new token. The component never notices.
or
Failure → catchErrorNavigates to /login?reason=session-changed&returnUrl=… and rethrows.

Single-flight refresh with shareReplay

Suppose the dashboard fires 5 calls and all 5 get a 401. Without protection that would mean 5 refresh calls. Here refresh() stores one inFlight observable, and shareReplay shares that one HTTP result with all 5 callers. So there is one refresh, and all 5 requests are replayed.

// session.service.ts
refresh(): Observable<string> {
  if (!this.inFlight) { this.inFlight = this.requestRefresh(); }
  return this.inFlight;                         // everyone gets the SAME observable
}
private requestRefresh() {
  return this.authService.refreshToken().pipe(      // POST auth/refresh
    map(r => { if (!restoreSession(r.access_token)) throw …; return r.access_token; }),
    catchError(err => { clearSession(); return throwError(() => err); }),
    finalize(() => { this.inFlight = null; }),       // ready for the next refresh
    shareReplay({ bufferSize: 1, refCount: false })   // 1 HTTP call, shared result
  );
}
Role-change safety: restoreSession() rejects a refreshed token whose role differs from the stored role. So if an admin changes your role, your next refresh ends the session and you log in again with the right menus.

// role-auth.ts
function activeTargets(tasks: Task[]): Set<string> {
  // skip COMPLETED, skip tasks without a target_id, skip target_type NONE
  set.add(`${task.target_type}:${task.target_id}`);      // e.g. "PRODUCT:42"
}
export function canEditRecord(tasks, targetType, targetId): boolean {
  if (!isWorker()) return false;
  return activeTargets(tasks).has(`${targetType}:${targetId}`);
}

// products-list.component.ts: managers OR a task on this record
canEditRecord(product: Product): boolean {
  return this.canManage || canEditByTasks(this.myTasks, 'PRODUCT', product.id);

fetchAll: reading every page

// api.service.ts
protected fetchAll<T>(requestPage, pageSize = 100): Observable<T[]> {
  return requestPage(1, pageSize).pipe(
    expand(res => res.page < res.total_pages ? requestPage(res.page + 1, pageSize) : EMPTY),  // keep asking for the next page
    reduce((all, res) => all.concat(res.items), [])                                         // join them into one array
  );
}

Every list API returns the same envelope: { items, total, page, page_size, total_pages }.

ORDER_PLACED→CONFIRMED→PROCESSING→PACKED→SHIPPED→OUT_FOR_DELIVERY→DELIVERED

The interceptor's 401 handling

return next(authorized).pipe(
  catchError((error: HttpErrorResponse) => {
    if (error.status !== 401 || authEndpoint) return throwError(() => error);  // no loop
    return session.refresh().pipe(
      catchError(refreshError => {                                  // ONLY catches refresh failure
        router.navigate(['/login'], { queryParams: { returnUrl: router.url, reason: 'session-changed' } });
        return throwError(() => refreshError);
      }),
      switchMap(newToken => next(withBearer(req, newToken)))      // replay once with the new token
    );
  })
);
Why is catchError above switchMap? So it only catches a refresh failure. If the replayed request fails for another reason, the session is not thrown away.

Proactive refresh timer

constructor() { effect(() => this.armFor(currentUser()?.access_token ?? null)); }

private armFor(token) {
  this.clearTimer();
  if (!token) return;                                         // logged out → no timer
  const delay = Math.max(0, tokenExpiry(token) - Date.now() - REFRESH_LEEWAY_MS); // 60 000 ms
  this.timer = setTimeout(() => this.refreshNow(), delay);
}

Likely questions

Why NgModules and not standalone?
It's the classic, well-documented style and easy to lazy load with loadChildren. Angular 17 supports both, and moving to standalone would only remove boilerplate.
Is hiding buttons enough for security?
No. Guards and hidden buttons are for user experience. The backend checks the role and the task on every write; it is the real security boundary.
You decode the JWT without checking the signature. Is that safe?
Yes. The client only uses the role and expiry to decide what to show. The server verifies the signature on every request. Editing the token locally only changes what the user sees; the API still refuses.
What if 5 requests get a 401 at the same time?
One refresh call. refresh() keeps one in-flight observable, and shareReplay shares its result. All 5 requests are replayed with the new token.
How do you avoid an infinite refresh loop?
Auth URLs are skipped. A 401 from auth/refresh is rethrown, and the replayed request sits outside the catchError.
How does pagination work?
Tables ask for one page of 10. For search and access checks, fetchAll uses expand + reduce to read all pages, 100 rows at a time.
What would you improve first?
The session restore on reload, the production API URL, an in-memory token, guards on add and edit routes, the delete lookup fix, server-side search and green tests.
How many APIs?
41 endpoints are defined across 10 resource services, and 38 are used. customers/{id}, orders/{id} and tasks/{id} are defined but unused.
If I had another week, I would fix the session restore on reload, keep the token in memory, add server-side search, tighten the add and edit route guards, and get the whole test suite green.
